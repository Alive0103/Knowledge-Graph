# 评测结果综合分析

## 1. 说明与数据来源

本文档对当前项目的三类实验结果进行统一分析：

1. 实体链接（Entity Linking, EL）
2. 实体对齐（Entity Alignment, EA）
3. 完整全流程评测（先实体链接，再实体对齐）

本次分析使用的结果文件如下：

- 实体链接
  - `work_wyy/trainlog/evaluation_report_llm_only_20260417_123957.json`
  - `work_wyy/trainlog/evaluation_report_vector_with_llm_20260418_214307.json`
  - `work_wyy/trainlog/evaluation_report_vector_with_llm_always_20260417_173023.json`
  - `retry/output/entity_linking_eval_data2_rigorous_full_20260331/text_only_metrics.json`
  - `retry/output/entity_linking_eval_data2_rigorous_full_20260331/vector_only_metrics.json`
- 实体对齐
  - `retry/output/experiment_comparison/zh_en_test_comparison.json`
  - `retry/output/experiment_comparison/zh_en_test_comparison_bge_m3_graph.json`
- 完整全流程
  - `retry/output/end_to_end_el_alignment_eval_20260418_222251/summary.json`
  - `retry/run_end_to_end_el_alignment_eval.py`

需要特别说明两点：

1. 实体链接评测基于 `find.xlsx`，共 `444` 条查询。
2. 全流程评测不是直接对 `444` 条全部样本做 EL->EA，而是只对其中既能映射到 `DBP15K zh_en` 中文侧、又具有英文侧金标准对齐的样本进行正式端到端评测。最终可用样本为 `93` 条，其中 `test=46`、`valid=47`。

这意味着：

- `444` 条结果适合评估实体链接模块本身。
- `1206` 对 `DBP15K test` 适合评估实体对齐模块本身。
- `93` 条 overlap 子集适合评估完整全流程的真实串联效果。

## 2. 实体链接结果分析

### 2.1 总体结果

当前共有 `5` 种实体链接方法：

1. `text_only`
2. `vector_only`
3. `llm_only`
4. `vector_with_llm`
5. `vector_with_llm_always`

在 `444` 条查询上的结果如下：

| 方法 | Query | MRR | Hits@1 | Hits@5 | Hits@10 |
| --- | ---: | ---: | ---: | ---: | ---: |
| text_only | 444 | 0.6536 | 0.5676 | 0.7635 | 0.8063 |
| vector_only | 444 | 0.0293 | 0.0158 | 0.0450 | 0.0698 |
| llm_only | 444 | 0.7385 | 0.6734 | 0.8131 | 0.8311 |
| vector_with_llm | 444 | 0.7332 | 0.6577 | 0.8198 | 0.8311 |
| vector_with_llm_always | 444 | 0.1396 | 0.1306 | 0.1509 | 0.1509 |

### 2.2 结果解读

#### 2.2.1 最优方法是 `llm_only`，但 `vector_with_llm` 非常接近

从 `MRR` 和 `Hits@1` 看，`llm_only` 是当前最强实体链接方法：

- `MRR=0.7385`
- `Hits@1=0.6734`

`vector_with_llm` 与其非常接近：

- `MRR=0.7332`
- `Hits@1=0.6577`

但 `vector_with_llm` 在 `Hits@5` 上略高于 `llm_only`：

- `vector_with_llm Hits@5=0.8198`
- `llm_only Hits@5=0.8131`

这说明混合检索策略确实提升了候选召回能力，但它并没有把这种召回优势稳定转化为更强的首位命中能力。换句话说，`vector_with_llm` 更像是“候选集更全”，而 `llm_only` 更像是“首位更准”。

#### 2.2.2 `text_only` 是很强的无 LLM 基线

`text_only` 的结果为：

- `MRR=0.6536`
- `Hits@1=0.5676`

它显著弱于 `llm_only`，但仍然处于可用水平，说明当前实体链接任务中，文本匹配和 ES 检索本身已经能覆盖大量样本。对于不希望引入 LLM 调用成本、推理时延或接口不稳定性的场景，`text_only` 是一个较强且稳定的工程基线。

#### 2.2.3 `vector_only` 基本不可用

`vector_only` 的结果仅为：

- `MRR=0.0293`
- `Hits@1=0.0158`

这不是“小幅落后”，而是“量级上的失败”。其表现说明：

1. 当前用于向量检索的表示方式并未有效对齐查询文本与目标实体。
2. 纯向量召回在该任务上无法替代文本检索或 LLM 推理。
3. 当前向量模块更适合作为候选补充，而不适合作为独立主方案。

#### 2.2.4 `vector_with_llm_always` 明显退化，不应作为主结果

`vector_with_llm_always` 的结果为：

- `MRR=0.1396`
- `Hits@1=0.1306`

它远低于 `llm_only` 和 `vector_with_llm`，甚至也远低于 `text_only`。结合之前的运行状态，这一模式在实际执行中包含大量 LLM 调用失败、回退与非稳定结果，因此它不能代表“更强的混合方法”，反而更像是“过度依赖 LLM 导致整体系统失稳”的反例。

这一结果的意义不是它“略差”，而是它说明：

- 在实体链接阶段，LLM 不是调用越多越好。
- 如果没有高质量候选约束与稳定输出控制，强制 LLM 介入会破坏排序质量。

### 2.3 实体链接阶段的阶段性结论

实体链接阶段可以得到以下结论：

1. 当前最强方法是 `llm_only`，在 `444` 条查询上取得了最高的 `MRR` 与 `Hits@1`。
2. `vector_with_llm` 与 `llm_only` 非常接近，说明向量召回有助于补充候选，但当前没有稳定转化为更强的首位排序。
3. `text_only` 是一个强且稳定的无 LLM 基线，适合作为工程保底方案。
4. `vector_only` 和 `vector_with_llm_always` 不适合作为主结果方法。

如果只从实体链接模块本身选择主方案，优先级应为：

1. `llm_only`
2. `vector_with_llm`
3. `text_only`
4. `vector_with_llm_always`
5. `vector_only`

## 3. 实体对齐结果分析

### 3.1 总体结果

当前共有 `4` 种实体对齐方法：

1. `raw_labse`
2. `raw_bge_m3`
3. `labse_neighbor_graph_model`
4. `bge_m3_neighbor_graph_model`

在 `DBP15K zh_en test` 的 `1206` 对测试样本上的结果如下：

| 方法 | Query | MRR | Hits@1 | Hits@5 | Hits@10 |
| --- | ---: | ---: | ---: | ---: | ---: |
| raw_labse | 1206 | 0.478 | 0.410 | 0.559 | 0.606 |
| raw_bge_m3 | 1206 | 0.679 | 0.624 | 0.745 | 0.776 |
| labse_neighbor_graph_model | 1206 | 0.696 | 0.631 | 0.773 | 0.810 |
| bge_m3_neighbor_graph_model | 1206 | 0.725 | 0.670 | 0.794 | 0.833 |

### 3.2 结果解读

#### 3.2.1 最优实体对齐方法是 `bge_m3_neighbor_graph_model`

从独立实体对齐任务看，最强方法是 `bge_m3_neighbor_graph_model`：

- `MRR=0.725`
- `Hits@1=0.670`
- `Hits@10=0.833`

这说明在“给定正确中文实体”的理想前提下，BGE-M3 表示与图增强结合，能取得最好的跨语言实体匹配效果。

#### 3.2.2 `raw_bge_m3` 已经非常强

`raw_bge_m3` 的结果为：

- `MRR=0.679`
- `Hits@1=0.624`

相比 `raw_labse`，它提升非常明显：

- `MRR` 提升 `+0.201`
- `Hits@1` 提升 `+0.214`

这说明对齐性能的主要跃升首先来自更强的文本表示，而不是图模型本身。换句话说，BGE-M3 主干已经把大量语义匹配能力直接带了进来。

#### 3.2.3 图模型对 LaBSE 的增益远大于对 BGE-M3 的增益

图增强对两类基础表征的增益并不相同：

- `raw_labse -> labse_neighbor_graph_model`
  - `MRR: 0.478 -> 0.696`
  - 增益 `+0.218`
- `raw_bge_m3 -> bge_m3_neighbor_graph_model`
  - `MRR: 0.679 -> 0.725`
  - 增益 `+0.046`

这说明：

1. 图结构信息对较弱的基础嵌入非常有效。
2. 当基础嵌入本身已经较强时，图增强仍有帮助，但边际收益明显变小。

因此，实体对齐阶段的总体规律是：

- “基础语义表示质量”决定下限与主体表现。
- “图模型增强”更多是在高质量基础表示之上的进一步微调优化。

### 3.3 实体对齐阶段的阶段性结论

实体对齐阶段可以得到以下结论：

1. 最强独立方法是 `bge_m3_neighbor_graph_model`。
2. 如果考虑实现复杂度与效果平衡，`raw_bge_m3` 也已经是非常强的方案。
3. `labse_neighbor_graph_model` 说明图增强本身有效，但它更多是弥补 LaBSE 基础表示不足。
4. 从模块视角看，实体对齐阶段的最佳主结果应写为 `BGE-M3 + neighbor graph model`。

## 4. 完整全流程结果分析

### 4.1 全流程评测口径

本次已补充正式的 EL->EA 串联评测脚本。其评测方式不是简单把 EL 和 EA 的单独结果并列，而是采用真正的串联过程：

1. 对 `find.xlsx` 的查询先做实体链接；
2. 只保留能映射到 `DBP15K zh_en` 中文侧 KG1 的实体候选；
3. 对每个候选中文实体运行实体对齐；
4. 依据“先 EL 排名、再 EA 排名”的规则展平英文候选列表；
5. 用英文侧金标准实体计算最终的 `MRR / Hits@1 / Hits@5 / Hits@10`。

样本分布如下：

| 指标 | 数值 |
| --- | ---: |
| `find.xlsx` 总样本 | 444 |
| 能映射到 KG1 的样本 | 407 |
| 具有对齐金标准的样本 | 93 |
| 其中 `test` 样本 | 46 |
| 其中 `valid` 样本 | 47 |

因此，完整全流程结果应分为两种口径理解：

1. `93` 条样本：当前所有可正式评测的 EL->EA 串联样本。
2. `46` 条样本：严格 `DBP15K test` 子集，更适合作为正式测试结论。

### 4.2 全流程 20 组组合结果概览

共有 `5 × 4 = 20` 组组合。

#### 4.2.1 `93` 条可评样本上的最好结果

最优组合是：

- `vector_with_llm + raw_bge_m3`
- `MRR=0.5249`
- `Hits@1=0.4731`
- `Hits@5=0.5806`
- `Hits@10=0.6882`

第二名是：

- `llm_only + raw_bge_m3`
- `MRR=0.5193`

两者差距非常小，仅 `0.0056` 个 `MRR`。

#### 4.2.2 严格 `test=46` 样本上的最好结果

最优组合是：

- `llm_only + raw_bge_m3`
- `MRR=0.5346`
- `Hits@1=0.5000`
- `Hits@5=0.5870`
- `Hits@10=0.6087`

第二名是：

- `vector_with_llm + raw_bge_m3`
- `MRR=0.5241`

两者差距同样较小，仅 `0.0105`。

#### 4.2.3 图模型在全流程中没有胜过 `raw_bge_m3`

这是本次分析最关键的现象之一。

在独立实体对齐任务中，最强方法是 `bge_m3_neighbor_graph_model`；但在完整全流程中，表现最好的 EA 组件不是图模型，而是 `raw_bge_m3`。例如：

- `vector_with_llm + raw_bge_m3` 的 `MRR=0.5249`
- `vector_with_llm + bge_m3_neighbor_graph_model` 的 `MRR=0.5105`

严格测试集上也一样：

- `llm_only + raw_bge_m3` 的 `MRR=0.5346`
- `llm_only + bge_m3_neighbor_graph_model` 的 `MRR=0.4546`

这说明一个重要事实：

> 独立模块最优，并不等于串联系统最优。

原因在于：

1. 独立 EA 评测默认输入的是“正确的中文实体”。
2. 全流程中，EA 接收到的是“EL 给出的候选实体”，其中包含错误候选与排序偏差。
3. 图模型在理想输入上更强，但在带噪声输入条件下，并没有表现出比 `raw_bge_m3` 更强的鲁棒性。

换句话说，`raw_bge_m3` 在全流程里更像一个“更稳的对齐器”，而 `bge_m3_neighbor_graph_model` 更像一个“理想条件下更优的对齐器”。

### 4.3 全流程各阶段之间的关系

#### 4.3.1 全流程上限首先由实体链接决定

完整全流程的第一个瓶颈不是实体对齐，而是实体链接是否把正确中文实体尽量放到前面。这个结论从结果非常明显：

- `llm_only`
- `vector_with_llm`

这两个 EL 方法在模块级结果上最好，因此它们在端到端上也组成了最好的两条主线。

反之：

- `vector_only`
- `vector_with_llm_always`

这两个 EL 方法在模块阶段已经失败，因此无论接哪个 EA 模型，端到端结果都很差。

#### 4.3.2 `text_only` 仍是可用的低成本全流程方案

`text_only + raw_bge_m3` 的结果为：

- `93` 条口径：`MRR=0.4375`
- `46` 条 test 口径：`MRR=0.3683`

虽然明显不如 `llm_only` 和 `vector_with_llm`，但仍然远好于 `vector_only` 和 `vector_with_llm_always`。这说明如果要构造一个不依赖 LLM 的完整系统，`text_only + raw_bge_m3` 是最合理的基础组合。

#### 4.3.3 `Answered` 指标在全流程里更接近“可组成完整排序”的覆盖率

在端到端结果中，很多组合的 `Answered` 很高，例如：

- `vector_only` 系列为 `93/93`
- `vector_with_llm_always` 系列为 `93/93`

这并不意味着它们表现好，而只意味着：

1. 这些方法至少返回了能映射到 KG1 的候选；
2. 一旦有候选可以送进 EA，就能构成一个完整英文排序；
3. 但最终金标准排名位置仍然可能很差。

因此，全流程评测时真正需要关注的核心指标是：

- `MRR`
- `Hits@1`

而不是只看 `Answered`。

## 5. 综合结论

### 5.1 如果分别看三个模块，最佳方案并不相同

从当前结果看：

1. **实体链接最佳方案**：`llm_only`
2. **实体对齐最佳方案**：`bge_m3_neighbor_graph_model`
3. **完整全流程最佳方案**：
   - `93` 条总可评样本上：`vector_with_llm + raw_bge_m3`
   - 严格 `test=46` 上：`llm_only + raw_bge_m3`

这说明项目的三个层次不能混为一谈。

如果论文只写“本项目最佳方法是某一个”，会掩盖一个很重要的实验事实：

> 最优实体对齐方法不是最优端到端方法；端到端最优由“实体链接质量 + 对齐器鲁棒性”共同决定。

### 5.2 当前最值得作为主结论的方法组合

如果从论文主结果的角度出发，建议这样写：

1. **模块级最优**
   - 实体链接：`llm_only`
   - 实体对齐：`bge_m3_neighbor_graph_model`
2. **系统级最优**
   - 完整全流程：`raw_bge_m3` 作为对齐组件时最稳
   - 最佳组合为 `llm_only + raw_bge_m3` 或 `vector_with_llm + raw_bge_m3`

更具体地说：

- 如果强调严格测试集，应使用 `llm_only + raw_bge_m3` 作为主结论。
- 如果强调当前全部可评样本，应使用 `vector_with_llm + raw_bge_m3` 作为主结论。

### 5.3 不建议作为主方案的方法

以下方法不建议进入正文主结果：

1. `vector_only`
2. `vector_with_llm_always`

原因不是它们略弱，而是它们与主方案差距过大，且表现不稳定或不可用。它们更适合作为反例或消融实验，用于说明：

- 纯向量检索不能替代文本或 LLM 推理；
- 过度依赖 LLM 调用会破坏实体链接稳定性。

## 6. 可直接写入论文的结论段

可直接使用以下表述：

> 实验结果表明，本系统在三个层面上呈现出不同的最优策略。实体链接任务中，`llm_only` 方法取得了最佳结果，在 `444` 条查询上达到 `MRR=0.7385`、`Hits@1=0.6734`，说明基于大语言模型的候选判断对复杂军事实体查询具有较强的首位命中能力。实体对齐任务中，`bge_m3_neighbor_graph_model` 在 `DBP15K zh_en test` 集上取得了最佳结果，达到 `MRR=0.725`、`Hits@1=0.670`，说明高质量语义表示结合图结构增强能够有效提升跨语言实体匹配性能。然而，在完整的“实体链接后再实体对齐”的端到端评测中，最优组合并非独立实体对齐任务中的最优模型，而是 `raw_bge_m3` 作为对齐组件时表现更稳。具体而言，在严格 `test` 子集上，`llm_only + raw_bge_m3` 取得了最佳端到端结果，达到 `MRR=0.5346`、`Hits@1=0.5000`。这一现象说明，端到端系统性能不仅取决于单模块上限，还强烈依赖于模块间误差传播与对噪声输入的鲁棒性。因此，项目的最终结论应区分“模块级最优”与“系统级最优”：前者强调 `llm_only` 与 `bge_m3_neighbor_graph_model` 的独立优势，后者则表明 `llm_only/vector_with_llm + raw_bge_m3` 是当前更适合作为实际系统主方案的组合。

## 7. 后续改进建议

基于当前结果，下一步最值得投入的方向不是继续强化 `vector_only`，而是优化 EL 与 EA 的衔接方式：

1. 将全流程评测扩展到更大的正式对齐样本集，减少当前 `93` 条 overlap 子集带来的样本限制。
2. 针对 EL 输出的噪声候选重新训练或蒸馏 EA 模型，而不是只在理想 gold 输入上训练 EA。
3. 尝试更合理的 EL->EA 融合方式，例如分数加权、联合重排，而不是单纯“先 EL、后 EA”的串联展平。
4. 保留 `raw_bge_m3` 作为当前系统级强基线，并把图模型优化重点放在“带噪声候选条件下的鲁棒性”上。

---

结论可以概括为一句话：

> 当前项目中，`llm_only` 是最强实体链接方法，`bge_m3_neighbor_graph_model` 是最强独立实体对齐方法，而 `llm_only/vector_with_llm + raw_bge_m3` 才是最优的真实端到端全流程方案。
